# OryxOS Go 逐节开发 Skill

## 概述

把且只把一节编号需求转化为经过验证的 OryxOS Go 增量。使用 Spec-Kit 控制执行流程，
使用项目 Harness 约束设计、依赖、测试和完成条件。

**核心原则：能由机器判定的事实使用硬门禁；需要产品或架构判断的事项停下等待用户确认。**

## 输入与事实来源

从用户请求中提取一个节号 `N`。仅接受 `16..31`；缺少节号或存在歧义时先询问用户。

产出任何制品前，必须按顺序完整阅读：

1. `docs/DemandAnalysis.md`——产品需求与阶段边界，最高事实来源；
2. `docs/TechnicalSolution.md`——实现设计；
3. `AGENTS.md`——仓库工程约束；
4. `docs/require/Harness 设计：用门禁保证每个功能符合预期.md`——执行门禁；
5. `docs/require/Spec-Kit 执行指导：从课件到代码（以第16节为例）.md`——执行流程；
6. `docs/require/第{N}节*.md` 的唯一匹配文件——本节需求。

不得使用其他课件目录作为事实来源或回退来源。节号文件不存在或匹配多个文件时，立即停下并报告精确匹配结果。现有代码只能证明当前状态，不能证明预期设计；行业研究只提供背景，不能扩大范围。

来源冲突时按上述优先级处理。课程文档只能在 `DemandAnalysis.md` 和 `TechnicalSolution.md`
划定的边界内细化实现，否则触发软门禁。

## 总纪律

### 硬门禁

- 测试、验证命令、依赖检查或交付物检查失败时不得继续推进。
- 行为变更使用测试先行：先写最小测试，观察它以预期原因失败，再写最小实现并持续保持全绿。
- 不得删除断言、放宽阈值、添加 `t.Skip` 或排除测试来制造全绿结果。
- 每个修改过的 Go 文件都必须执行 `gofmt`。
- 以下仓库门禁全部通过后，一节课才可能完成：

```bash
go test ./...
go vet ./...
CGO_ENABLED=0 go build ./cmd/oryxos
```

仓库已经配置且与本次范围相关的 lint、安全或 CI 检查也是附加硬门禁。只有亲眼看到当前命令输出后，才能声称检查通过。

### 软门禁

遇到下列任一情况，立即停下、报告证据并等待确认：

1. 所需导出类型、方法、配置键、数据库字段或表、REST 路径、Profile 字段、CLI 叶子命令或其他公共概念，在事实来源中没有依据；
2. 必须修改已经确定的字面量、公共签名、Schema、端点、固定数量或阶段边界；
3. 两个事实来源发生冲突；
4. 必须修改前序课程的公共契约，且当前课程没有明确把它列为改造点；
5. 无法在当前 Go Module 版本的本地依赖中核实第三方 API；
6. 需要新增 plan 未批准的依赖；
7. 请求内容属于扩展阶段，但当前 feature 的范围是核心阶段。

全程不得自动 commit、push、发布、打包、改写无关用户变更或丢弃脏工作区。Git 同步时机由用户决定。

## 课型分流

| 节号 | 课型 | 处理方式 |
|---|---|---|
| 16、17、18、19、20、22、24、25、26、29、30 | 代码课 | 执行下方完整流程。 |
| 21、23 | 评审课 | 不产码，只作为第 22 或 24 节的需求输入。 |
| 27、28 | 串联课 | 不创建新功能规格；执行当节对账清单，并用 `//go:build integration` 把要求的流程固化为 Go 集成测试。 |
| 31 | Demo／发布课 | 只组装和验证两个既定 Demo 及文档规定的发布清单，不得发明第三个 Demo。 |

课型分流不能覆盖阶段边界。动态 Agent 管理或额外 REST 路径一旦超过核心阶段固定数量，必须触发软门禁。

## 代码课完整流程

### 第 0 步：开工与依赖门禁

1. 完整阅读本节需求和 `TechnicalSolution.md` 对应内容：

| 节号 | `TechnicalSolution.md` 重点 |
|---|---|
| 16 | Provider、Profile、`llm_calls` |
| 17 | ReActLoop、AgentService、Prompt／Context、`tool_invocations` |
| 18 | CLI／Channel、SessionService、`sessions` |
| 19 | Notify Tool 与通知渠道 |
| 20 | ToolRegistry、ToolExecutor、内置 Tool、MCP |
| 22 | Markdown Memory |
| 24 | Sandbox |
| 25 | Scheduler 与 Session 身份 |
| 26 | Gin Web Service 与精确 REST 契约 |
| 29 | Skill + Profile 运行时组合 |
| 30 | Agent 生命周期／动态管理；规划前先核对阶段范围 |
| 27、28、31 | 端到端流程与两个 Demo |

2. 从 `docs/require/` 阅读所有前置代码课的“本节交付物”，检查仓库中所需包、导出符号、Schema、配置制品和测试。缺少前置课程文档或交付物时，停下报告“先完成第 X 节”，不得在当前课程中重造依赖。
3. 检查 `git status`、当前分支／工作树、模块路径、`go.mod` 和已有测试。未经用户授权，不得切换分支或创建工作树。
4. 记录候选文件、与用户变更的重叠、可执行检查和未解决冲突。

### 第 1 步：定义“做什么”与“为什么”

**必须使用子技能：** `speckit-specify`。

只从课程的目的和边界章节组装输入：

```text
第{N}节需求：<模块名>——<一句话定位>
背景与价值：<为什么需要>
用户场景：<2～3 个可观察场景>
功能需求：FR1..FRn，每条可独立测试
明确不做：原样保留课程排除项，不扩大范围
验收标准：把自动检查映射到课程 Harness；列出剩余人工检查
依赖与假设：列出前置课程交付物和已经核实的外部依赖
```

规格文档中不写导出 Go 标识符、包位置、库或 Schema。

### 第 2 步：澄清歧义

**必须使用子技能：** `speckit-clarify`。

答案只能来自事实来源。需要发明答案或仲裁来源时，触发软门禁，不得猜测。

### 第 3 步：规划“怎么做”

**必须使用子技能：** `speckit-plan`。

计划必须写明：

- Go 1.26+ 以及 `AGENTS.md` 和 `TechnicalSolution.md` 中与本节相关的精确技术栈；
- 运行时以 Eino core `model.ToolCallingChatModel` 为边界，Eino-ext 只出现在 Provider 工厂中，禁止 Eino ADK 自动执行 Tool；
- 按当前依赖方向放入 `internal/`。不得机械翻译 Java 模块名，必须使用 `AGENTS.md` 和 `TechnicalSolution.md` 规定的 Go 包结构；
- 涉及时必须保持模型实例按 Profile 隔离、同步 JSON、Tool 串行执行、`context.Context` 贯穿、纯 Go SQLite 和所有核心固定数量；
- 凭证使用环境变量占位符，日志和错误必须脱敏；
- 本节测试文件与关键回归行为。单测默认执行；真实网络冒烟使用 `//go:build integration`，并通过 `go test -tags=integration` 显式运行；
- 不得增加事实来源以外的依赖、导出契约、数据库对象、端点、CLI 命令或延后功能。

写出第三方构造函数、选项函数、方法或接口形状之前，必须用 `go doc`、模块缓存和
`go.mod`／`go.sum` 核实。教程示例代码不能作为 API 存在性证据。

### 第 4 步：生成任务并停下

**必须使用子技能：** `speckit-tasks`。

把 `tasks.md` 与课程完整交付物逐项比较，包括生产文件、测试、配置、Schema／Migration、文档更新和人工验证。确认每项行为的失败测试任务早于或伴随对应实现任务。

报告缺失项、多余项、顺序问题和范围冲突，然后停止等待用户确认。即使比对完全一致，tasks 后的固定确认点也不得跳过。

### 第 5 步：确认后分析并实现

先用 `speckit-analyze` 检查 spec／plan／tasks 一致性，再用 `speckit-implement` 执行。

每个实现任务都必须：

1. 写代码前核实第三方 API；
2. 先写最小且有意义的测试，并观察它因目标行为尚未实现而失败；
3. 只实现本节交付物，保留既有字面量与公共契约；
4. 把 Eino-ext、Gin、Cobra、GORM 和 MCP 依赖留在文档规定的边缘层；
5. Go 测试标识符使用 ASCII 英文 `Test...`；需要与课程对号时，可在子测试名或注释中保留中文原文。示意代码必须适配真实 API，但断言行为逐条保真；
6. 运行目标包测试，格式化修改过的 Go 文件，失败立即修复。

不得积攒红灯测试，不得为排除项创建推测性抽象或占位实现。

## 串联课与 Demo 模式

第 27 或 28 节使用对应 `docs/require` 文档中的精确清单和测试名称。端到端测试放在当前仓库测试约定要求的位置，并使用 `//go:build integration`。先运行普通回归门禁，再显式运行集成测试。

第 31 节只验证 `weather-daily` 和 `daily-tech-digest`，两者都必须支持定时触发和通过共享
`AgentService.Invoke` 路径人工补跑。保持 2 个 Provider、9 个 Tool、10 个端点、12 个命令、3 张表、2 个 Demo 以及工作区目录／文件数量精确不变。网络调用和凭证只能列为人工证据，除非用户授权执行。

## 节级完成契约

宣布本节完成前必须收集全部证据：

1. 修改文件的 `gofmt` 检查、`go test ./...`、`go vet ./...` 和无 CGO 构建全部通过；
2. 每个 Harness 测试都存在、非空、实际运行过，并能映射到对应回归行为；
3. 每项课程交付物都存在于批准的包／路径中，没有出现额外公共概念；
4. 所有前序课程测试保持全绿；
5. 按当前仓库状态复查全局不变量：
   - 文件、命令和 HTTP 等外部操作经过应用层 Sandbox；
   - 每次 LLM 与 Tool 调用，包括失败调用，都写入规定的核心记录；
   - 凭证只来自环境变量且始终脱敏；
   - Session 身份只由 SessionService 生成；
   - `context.Context` 贯穿调用链，Tool 串行执行，不引入未批准的 goroutine 编排；
   - ReActLoop 保有 Tool 执行权，不存在 Eino ADK 自动执行路径；
   - `runtime` 与 `web` 的依赖边界保持正确；
   - 核心阶段只存在三张 SQLite 表，无 CGO 单二进制契约保持有效；
6. 列出没有执行的人工检查，例如真实 Provider、MCP、Webhook、网络、定时时钟或发布冒烟。人工项不得被静默报告为已通过。

## 最终报告

以实际 `git status --short` 和 `git diff --stat` 为证据，报告：

- **状态：** 完成、未完成或阻塞，以及原因；
- **改动：** 按 Go 包／配置／测试／文档分组列出文件及动机，突出说明触碰过的前置课程文件；
- **重点评审：** 按风险排序列出 3～6 项，并提供文件和行号；
- **验证：** 每条命令、精确结果和目标 Harness 映射；
- **范围：** 交付物是否齐全、排除项是否保留、核心固定数量是否不变、是否存在来源冲突；
- **人工检查：** 剩余操作、精确命令和预期结果。

报告结束后停止。可以建议提交信息，但不得执行 commit、push、打包或发布。

## 常见错误

- 把 Java 包名或类名直接翻译成 Go，而不是遵守 Go 包边界；
- 把课程说明或示例 Connector 名称置于 `DemandAnalysis.md` 之上；
- 只按 Provider 缓存模型实例，而不是按 Profile 隔离；
- 让 Eino ADK 执行 Tool，或者并行执行多个 Tool Call；
- 增加扩展端点、数据表、CLI 叶子命令、fallback、SSE、认证或第三个 Demo；
- 使用 `mattn/go-sqlite3`、Shell 字符串、未经检查的重定向或泄漏凭证；
- 单测通过后跳过 `go vet` 或无 CGO 构建，却宣称完成。
